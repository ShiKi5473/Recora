# 匯出檔案大小預估的校正

這個工具在手機上自動跑一批剪輯匯出。它從 debug build 的 logcat（tag `RecoraExport`）收集每一支的預估大小、實際大小和原檔資料量。

## 用法

```bash
# 先 build 並安裝 debug 版：JDK 21 = "C:/Program Files/Android/Android Studio1/jbr"
bash tools/calibration/calibrate.sh tools/calibration/jobs-astro-holdout.txt
```

- **jobs 檔格式：** 寫在 `calibrate.sh` 開頭，每行是「編碼|解析度|畫質|檔名|起點秒|長度秒|去除聲音」。檔名就是相簿裡的檔名。
- **怎麼驅動 App：** 腳本用 `adb shell am start` 帶 extras 給 debug 版的 `MainActivity`。App 先改匯出設定，再開剪輯畫面、設好範圍。等量完原檔這一段，就呼叫和手動按「匯出」同一個 `export()`。整個過程不模擬點擊，所以不需要「USB 偵錯（安全設定）」。
- **速度：** 每支約 10～15 秒，轉檔本身只占 3～5 秒。
- **螢幕要亮著：** 腳本會設 `svc power stayon true`，每支開始前也會喚醒螢幕。螢幕一關，播放器就讀不到規格，那一支會逾時。
- **結果：** `out/results.log` 一支一行，過程在 `out/progress.log`，逾時的截圖也在 `out/`。
- **改回設定：** 跑完會把匯出設定改回 `RESTORE` 指定的值，預設是 H.265・原始解析度・標準。腳本會從 log 確認有沒有改成功。
- **測試檔：** 匯出的檔案會存進相簿（Movies/Recora），跑完記得清掉。

log 欄位說明：

| 欄位 | 意思 |
|---|---|
| `estimate` | 預估大小，含學到的修正倍數，所以會受跑的順序影響 |
| `actual` | 實際大小 |
| `videoBps` | 要求編碼器的位元率；「不重新編碼」時是原檔平均位元率 |
| `predictedBps` | 公式預估的實際輸出影像位元率，還沒乘上修正倍數 |
| `srcVideoBytes` / `srcAudioBytes` | 原檔在這段範圍內的實際資料量；debug 版不論哪種編碼都會量 |
| `factorKey` / `factorBefore` / `measured` | 倍數的 key、匯出前已學到的倍數、這次測到的倍數 |
| `tookMs` | 匯出本身花的時間 |

分析時用 `actual`、`srcVideoBytes`、`videoBps`、`clipMs` 離線重算，不要直接看 `estimate`。

## 目前的結論（2026-10-15）

**不重新編碼**：已經解決，誤差在 ±0.5% 以內。做法是加總選取範圍內原檔的實際資料量：
- MP4 用 MediaExtractor 量。
- TS 用 `TsRangeBytes` 自己解析。Android 的 MediaExtractor 讀不到 Mufu TS 裡的 H.265 主串流。

**重新編碼，Mufu（TS）**：預估 = 要求的位元率 × 學到的倍數。倍數依「編碼｜輸出高度｜畫質｜來源容器」分開記。Mufu 的位元率很穩定，誤差在 ±3% 以內。

| 設定 | 倍數 |
|---|---|
| H.264 1440p 標準 | 1.20～1.25 |
| H.264 1080p 省空間 | 1.91～1.97 |
| H.265 1440p 標準 | 1.23～1.26 |

**重新編碼，Astro（MP4）**：Astro 每段畫面的複雜度差很多。同一個要求，實際輸出從 0.2 到 1.25 倍都有，而且幾乎完全跟著原檔這一段的位元率走。所以改用 `ExportOptions.complexityBitrate` 預估：

```
影像位元率 = min(固定值 + 原檔這段的位元率 × √(輸出像素 ÷ 原檔像素) × 原檔倍數 + 要求的位元率 × 要求倍數,
                1.25 × 要求的位元率)
```

| 編碼 | 固定值 | 原檔倍數 | 要求倍數 | 擬合用的支數 |
|---|---|---|---|---|
| H.264 | 0.4 Mbps | 1.48 | 0.06 | 47 |
| H.265 | 0 | 0.90 | 0.22 | 55 |

- **1.25 倍上限：** 小米的編碼器輸出最多到要求的 1.25 倍。複雜的畫面在 H.264 和 H.265 都停在這裡。
- **簡單的畫面：** 不管要求多少，輸出都差不多。例如 004698F 在 H.265 標準和高畫質都是約 4.2 Mbps，所以要求的位元率只占一小部分。
- **縮小解析度：** 原檔的部分乘上像素比例的平方根，也就是長寬的比例。直接乘像素比例，1080p、720p 會低估約 20%。
- **修正倍數：** 公式之外，再依設定學一個修正倍數，key 是 `…|MP4/src`。每次只吸收新值的 2 成，並限制在 0.7～1.4，不會被單一支影片洗掉。舊的做法是新舊各占一半，同一個設定的倍數曾在 0.58～1.17 之間跳，誤差從 −36% 到 +278%。

各設定用公式離線重算的誤差（還沒乘修正倍數）：

| 設定 | H.264 均方根（最大） | H.265 均方根（最大） |
|---|---|---|
| 1440p 標準 | 13.7%（31%） | 11.2%（26%） |
| 1440p 省空間 | 6.7%（18%） | 8.9%（17%） |
| 1440p 高 | 16.3%（37%） | 21.4%（37%） |
| 1080p 標準 | 14.2%（25%） | 15.1%（27%） |
| 720p 標準 | — | 13.3%（22%） |

- **剩下的誤差：** 主要來自畫面內容。少數片段原檔位元率低、畫面卻複雜，例如前鏡頭 004646F，每種設定都低估 30% 以上。只看原檔位元率改善不了。
- **高畫質：** 在兩種編碼都平均偏低 9～13%，修正倍數用幾次之後會補上。

## 資料

- `history-2026-10-15.log`：今天 103 支的結果。
  - H.264 和 H.265 1440p 標準各 12 支，對應 `jobs-astro-h264.txt`、`jobs-astro-h265.txt`。
  - 沒用過的 11 支各跑兩種編碼，對應 `jobs-astro-holdout.txt`。
  - 8 支 × 7 種解析度和畫質，對應 `jobs-astro-settings.txt`。
- `history-2026-10-14.log`：昨天的資料。其中 `Original|TS` 有 5 筆 `estimate` 只有實際大小的十分之一，那是 TS 解析修正前的錯誤量測，分析時要排除。
- 同一段影片用同一個設定重新編碼，輸出大小每次都一樣。所以重跑擬合用過的片段只能確認程式算得對，要看公式準不準得用沒用過的片段。

## 還沒做

- **跨段剪輯：** intent 只帶一個檔名，所以腳本只支援單段。
- **Mufu TS 改用畫面複雜度公式：** Mufu 誤差本來就小。而且 H.265 原檔的係數一定和 H.264 原檔不同，要另外擬合。
